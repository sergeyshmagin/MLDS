# UrbanStay: прогноз отмены бронирования

Модель предсказывает вероятность отмены брони и переводит прогноз в деньги через метрику
Incremental Revenue (IR). Проект выполнен на данных PostgreSQL сети отелей UrbanStay:
`hotel_bookings` (35 341 бронь) и `hotel_reviews` (25 177 отзывов).

**Результат на тестовой выборке:** доля отмен 25.58% -> 12.25%, загрузка 74.42% -> 65.30%,
доход +25.67% (47.71 млн руб. на 5 902 брони, 8 084 руб. на бронь). **Ни одна из трёх целей
заказчика не достигнута**: 10% отмен, падение загрузки не более 8% и прирост дохода 50%
недостижимы при текущем качестве данных. Разбор причин - в выводах тетради.

Разбиение выборок хронологическое (train 2017-2019, calibration 2019-2020, test 2020-2025),
кросс-валидация - `TimeSeriesSplit`, калибровка обучена на временных out-of-fold прогнозах,
порог выбран строго по максимуму IR.

## Важно: модуль с тем же именем есть в прошлых спринтах

`feature_pipeline.py` называется так же, как модули из SPRINT_13 и SPRINT_14, но содержит
другой код. Если рядом с тетрадью (или в домашней папке JupyterHub) лежит старая версия,
тетрадь упадёт с `AttributeError: module 'feature_pipeline' has no attribute 'RANDOM_STATE'`.

Что делать: положить `feature_pipeline.py` из этого спринта в ту же папку, где лежит тетрадь,
перезаписав старый файл, и **перезапустить ядро** - Python кэширует уже импортированные модули.
Тетрадь проверяет это сама: в модуле есть маркер `SPRINT = "SPRINT_18"`, и при несовпадении
первая ячейка падает с понятным сообщением и печатает путь к подхваченному файлу.

## Инференс на новых данных

```python
import joblib
import pandas as pd
import feature_pipeline as fp

artifact = joblib.load("artifacts/model.joblib")
model = artifact["pipeline"]               # CalibratedBookingModel из feature_pipeline
threshold = artifact["threshold"]          # рабочий порог 0.395, не 0.5
with_demand = artifact["with_demand"]      # включены ли признаки спроса

bookings = fp.clean_bookings(new_bookings_raw)   # сырая выгрузка hotel_bookings
reviews = fp.clean_reviews(reviews_raw)          # сырая выгрузка hotel_reviews
merged = fp.add_demand_features(fp.join_reviews(bookings, reviews))
features = fp.build_features(merged, with_demand=with_demand)

probability = model.predict_proba(features)[:, 1]
risky = probability >= threshold                 # брони, по которым стоит принимать меры
```

## Порог

- **0.395 - рабочий порог**, сохранён в артефакте. Выбран строго по максимуму IR на
  калибровочной выборке, без дополнительных условий: бизнес-ограничения проверяются
  отдельно, на этапе расчёта экономической эффективности.
- Он в точности совпал с аналитическим порогом безубыточности
  `(AvgRev + CostFP) / (PerRebooking + LostRev + AvgRev + CostFP) = 0.395`, что подтверждает
  близость калиброванных вероятностей к фактическим долям.
- Этот же порог используется на кросс-валидации как фиксированная точка сравнения
  конфигураций: подбирать порог внутри валидационного фолда нельзя, иначе оценка становится
  оптимистичной.

Экономические параметры (`AvgRev`, `CostFP`, `LostRev`, `PerRebooking`) заданы константами
в `feature_pipeline.py`. При их пересмотре порог нужно пересчитать функцией `fp.threshold_scan`
на свежей калибровочной выборке.

## Ограничения данных

- **Отзывы нельзя связывать с бронями по клиенту.** Отзыв есть у всех состоявшихся броней и
  ни у одной отменённой, поэтому связь через `booking_id` даёт признак, который однозначно
  определяет целевую переменную. Объединение выполняется только по дате: каждой брони достаётся
  последний отзыв, оставленный строго до её оформления.
- **Признаки отзывов в модель не входят.** Одна и та же запись достаётся всем броням одного
  дня (14.5 брони на отзыв), то есть характеризует календарный день и постороннего гостя.
  Объединение и векторизация остались в тетради как исследовательский этап.
- Брони с нулевой стоимостью удаляются, а не восстанавливаются импутацией: минимальная
  ненулевая цена 6 700 руб., поэтому ноль здесь - некорректная запись. После очистки
  остаётся 29 504 брони.
- Номерного фонда в выгрузке нет, поэтому загрузка считается от числа броней (одна бронь -
  один номеро-период). Уровни загрузки нельзя сравнивать с плановыми 80% заказчика напрямую -
  корректно сравнивать динамику, на которую это допущение не влияет.
- Качество модели упирается в ROC-AUC около 0.81. Это проверено четырьмя гипотезами (признаки
  спроса, нативные категории CatBoost, блендинг, расширенный поиск Optuna) - ни одна прироста
  не дала. Дальнейший рост требует новых данных: `customer_id` в таблице броней и условий тарифа.
